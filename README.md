# Cell Count Dashboard

Analysis and interactive dashboard for immune cell population data across clinical samples.

---

## Dashboard

**http://localhost:8050/dashboard.html**

Run `make dashboard` to start the server (see instructions below). In GitHub Codespaces, the URL will be different — open the Ports tab, find port 8050, and click the forwarded link, then append `/dashboard.html`.

---

## Running the Code

Tested with Python 3.9+. All dependencies are listed in `requirements.txt`.

```bash
make setup      # install pandas, scipy, matplotlib
make pipeline   # run the full analysis and generate all outputs
make dashboard  # build the dashboard and start the local server
```

### Reproducing outputs

`make pipeline` runs `load_data.py` and produces everything from scratch:

| Part | Description | Output |
|------|-------------|--------|
| 1 | Load `cell-count.csv`, build SQLite database | `cell-count.db` |
| 2 | Compute relative frequencies per sample | `relative_frequencies` table in DB, `output.txt` |
| 3 | Mann-Whitney U tests (responders vs non-responders) | `output.txt`, `plots/*.png` |
| 4 | Baseline subset summary (melanoma · miraclib · PBMC · time=0) | `output.txt` |

`make dashboard` then regenerates `dashboard.html` from that data and starts a server at port 8050.

### GitHub Codespaces

1. Run `make setup`, then `make pipeline`, then `make dashboard`.
2. Codespaces will detect port 8050. Go to the **Ports** tab, click the globe icon next to port 8050.
3. Add `/dashboard.html` to the end of the URL that opens.

## Database Schema

Three tables:

**`samples`** — one row per sample with all metadata.

```sql
CREATE TABLE samples (
    sample                    TEXT PRIMARY KEY,
    project                   TEXT,
    subject                   TEXT,
    condition                 TEXT,
    age                       INTEGER,
    sex                       TEXT,
    treatment                 TEXT,
    response                  TEXT,
    sample_type               TEXT,
    time_from_treatment_start INTEGER
);
```

**`cell_counts`** — one row per (sample, population) pair, in long format.

```sql
CREATE TABLE cell_counts (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    sample     TEXT REFERENCES samples(sample),
    population TEXT,
    count      INTEGER
);
```

**`relative_frequencies`** — cached output of the Part 2 query (sample, total_count, population, count, percentage).

### Design rationale

Cell counts are in long format rather than wide columns (`b_cell`, `cd8_t_cell`, …). Adding a new cell population is just new rows — no migration needed. Aggregation is also simpler: per-sample totals are a `GROUP BY sample`, and filtering to specific populations is a `WHERE population IN (...)`.

Sample metadata lives in its own table so joins are explicit and queries stay focused — a per-population analysis doesn't need to carry patient age and sex through every row.

`relative_frequencies` is stored as a precomputed table rather than a view so it can be queried directly without re-running the CTE each time.

### Scaling to hundreds of projects and thousands of samples

The normalized structure holds up well as data grows:

- **Query performance**: add indexes on `cell_counts(sample, population)` and on the `samples` columns used for filtering (`condition`, `treatment`, `sample_type`, `response`).
- **New cell types**: no schema change needed — just insert new rows with the new population name.
- **New analytic types**: a `time_from_treatment_start` column already supports longitudinal queries. For survival analysis or mixed models you'd join to `samples` and filter by subject. For multi-cohort comparisons, `project` is a first-class column you can group by directly.
- **New data modalities** (proteomics, RNA, etc.): add an `assay_type` column to `cell_counts`, or keep a separate `measurements` table with an assay foreign key, depending on how different the data shapes are.
- **Very large datasets**: partition `cell_counts` by project, or migrate to a columnar store (DuckDB, BigQuery) if row counts reach tens of millions. The query patterns used here (aggregation, filtering, joins) translate directly.
- **Access control**: add a `projects` table with ownership/permissions and join on `project` to scope queries per user.

## Code Structure

```
cell-count-dashboard/
├── load_data.py            # analysis pipeline (Parts 1–4)
├── generate_dashboard.py   # builds dashboard.html from the data
├── dashboard.js            # chart rendering and interactivity (Plotly.js)
├── dashboard.css           # styles
├── dashboard.html          # generated — open in a browser
├── cell-count.csv          # input data
├── plots/                  # generated boxplots
├── requirements.txt
└── Makefile
```

### Why it's structured this way

The pipeline (`load_data.py`) and the dashboard (`generate_dashboard.py` + `dashboard.js`) are kept separate because they serve different purposes. The pipeline writes to the database and generates static outputs; the dashboard reads from the source CSV and is regenerated on demand. This means you can rerun the analysis without touching the dashboard code, and update the dashboard without rerunning the pipeline.

The dashboard is a static HTML file rather than a Python server (e.g. Dash) so there are no runtime dependencies once it's built — it runs in any browser from a simple file server.

**`load_data.py`** has four functions called in order by `main()`:
- `initialize_database` — creates the schema and loads the CSV into `samples` and `cell_counts`.
- `find_relative_freqs` — computes per-sample relative frequencies with a CTE query and saves the result back to the DB.
- `statistical_analysis` — filters to the melanoma/miraclib/PBMC subset, runs Mann-Whitney U tests per population, saves boxplots to `plots/`.
- `subset_analysis` — prints the baseline (time=0) breakdown by project, response, and sex.

When run as `__main__`, stdout is redirected to `output.txt`.

**`generate_dashboard.py`** re-runs the statistical tests, serializes all data to JSON, and writes `dashboard.html`. The HTML injects four globals (`ALL_DATA`, `STAT`, `POPULATIONS`, `POP_LABELS`) as an inline script, then loads `dashboard.js`. A local HTTP server is needed only so the browser can fetch the external JS and CSS files via relative paths.

**`dashboard.js`** reads those globals and renders three tabs:
- *Data Overview* — filterable paginated table of relative frequencies per sample and population (sample, total_count, population, count, percentage).
- *Statistical Analysis* — Mann-Whitney p-value summary, per-population boxplot and scatter plot with trendlines.
- *Subset Analysis* — KPI cards, samples per project, and response/sex breakdowns for the baseline cohort.

**`dashboard.css`** contains all styles. No inline styles are used in the HTML — hidden tabs use a `.tab-hidden` class toggled by JavaScript.
